# Assets & baking

DreamCart games ship as a tiny JavaScript bundle plus, optionally, one binary
asset blob. Anything heavier than code — bitmap fonts, sprites, glTF meshes,
animations, textures, data-driven scenes, imported BSP maps — is **baked**
offline into compact data, then loaded by the runtime with no parsing tax.

Baking happens at build time on [Bun](getting-started). It does the expensive,
floating-point-heavy work (PNG decode, mesh interleaving, animation resampling,
quaternion math) **once**, on a fast desktop, and emits exactly the bytes the
target hardware uploads. The PSP, the Web, and the 3DS then array-look-up and
draw — no trigonometry, no decoders, no megabyte source parse at boot.

## Why bake at all

The runtime is [QuickJS](runtime-contract) on hardware as small as a 32 MB PSP.
Two costs dominate when a game carries assets inline:

1. **Tokenizing string literals.** The old pipeline embedded each baked blob as a
   base64 string literal in the bundled game JS (`new Float32Array(unb64('AACA…').buffer)`).
   The PSP host bakes that JS into the EBOOT and evaluates it with QuickJS at
   boot — so QuickJS had to tokenize *megabytes* of string literals (1.28 MB for
   one soldier model alone).
2. **Base64-decoding** those literals at startup.

Together these were the dominant cost of loading an asset-heavy game. The bake
pipeline removes both by moving the bytes out of the JS source and into a single
binary container — the [`.dcpak`](#the-dcpak-container) pack — read straight as
typed arrays.

## The bake pipeline

One command runs every baker in order:

```bash
bun run bake
```

which expands to:

```bash
bun framework/bake/bake-font.ts
bun framework/bake/bake-sprites.ts
bun framework/bake/bake-gltf.ts
bun framework/bake/bake-scene.ts
bun framework/bake/bake-bsp.ts box
bun framework/bake/bake-bsp.ts zfight
```

`bake` is the first step of the umbrella `bun run build`
(`bake → typecheck → bundle → web`), so a normal build always re-bakes.

Each baker reads a source asset (a font header, sprite definitions, a `.glb`, a
scene descriptor, a `.bsp`) and writes a small **TypeScript data module** under
`framework/src/assets-*.ts`. The heavy byte payloads do **not** live in those
modules — they go into one binary **master store**, `framework/src/assets.dcstore`
(itself a `.dcpak` file). The generated `.ts` module keeps only the structural
skeleton (scalars, joint tables, AABBs, clip metadata) plus the **string keys**
that name each blob in the store.

| Baker | Input | Output module | Payload |
|-------|-------|---------------|---------|
| `bake-font.ts` | `font8x8_basic.h` (public-domain 8×8 ASCII) | `assets-font.ts` | inline (tiny) |
| `bake-sprites.ts` | `bake/sprite-defs.ts` row/palette defs | `assets-sprites.ts` | inline (tiny) |
| `bake-gltf.ts` | vendored `.glb` (Fox, Kenney car, Kenney nature) | `assets-fox.ts`, `assets-kenney-car.ts`, `assets-kenney-nature.ts` | `assets.dcstore` |
| `bake-scene.ts` | `SceneDescriptor` exports | `<key>:scene.*` blobs | `assets.dcstore` |
| `bake-bsp.ts` | GoldSrc/Half-Life `.bsp` v30 | `assets-bsp-*.ts` | `assets.dcstore` |

Fonts and sprites are small enough to stay inline; everything large lands in the
store. See [World import](worlds) for the BSP map pipeline.

### Fonts

`bake-font.ts` parses the 8×8 bitmap font header (`bit0` = leftmost pixel, the
order the [Graphics](framework) text routine expects) and emits a `Font` whose
glyphs are just row bitmasks, with per-glyph trimmed widths:

```ts
// AUTO-GENERATED by bake/bake-font.ts
export const FONT8X8: Font = {
  height: 8,
  glyphs: {
    65: { w: 6, rows: [12,18,33,33,63,33,33,0] }, // 'A'
    // …ASCII 32–126
  },
  fallback: { w: 6, rows: [62,34,34,34,34,34,62,0] },
};
setFont(FONT8X8);
```

### Sprites

`bake-sprites.ts` turns palette-indexed row definitions into framework
`Bitmap`s via `bitmapFromRows`, so a game just draws them with the 2D
[Graphics](framework) API:

```ts
// AUTO-GENERATED by bake/bake-sprites.ts
export const SPRITES: Record<string, Bitmap> = {
  "player": bitmapFromRows(["..XX..", ".XXXX."], { "X": 0x33cc55 }),
};
```

### glTF meshes, skins, animation & textures

`bake-gltf.ts` is the heavyweight. It reads each vendored `.glb` with
`@gltf-transform/core`, bakes node transforms into geometry, interleaves vertices
in the [g3d](3d) hardware order, decodes and downsamples PNG textures, and (for
skinned rigs) resamples animation clips to fixed-rate frames. Output blobs go to
`assets.dcstore`; the generated module references them by key.

A baked mesh is described by a `BakedMesh` (declared in `framework/src/mesh.ts`):

```ts
export interface BakedMesh {
  format: number;       // FMT_* bitfield from g3d.ts
  stride: number;       // bytes per vertex == vertexStride(format, weightCount)
  vertexCount: number;
  weightCount: number;  // f32 bone weights/vertex when FMT_WEIGHTS (else 0)
  triCount: number;
  aabb: { min: [number, number, number]; max: [number, number, number] };
  vertices: Uint8Array; // interleaved, GE order
  indices: Uint16Array; // triangle list
}
```

Vertices are interleaved in the GE-mandated order
`[weights][uv][color][normal][position]` (each field present only if its format
bit is set, 4-byte aligned). For example the Kenney nature props bake to
`format = 7` (`COLOR | NORMAL | POS`), `stride = 28`, color folded per-vertex
into a packed ABGR `u32` so they need no texture at all:

```ts
// AUTO-GENERATED by bake/bake-gltf.ts from Kenney Nature Kit (CC0).
import { dcU8, dcU16 } from './dcpak';
export const NATURE_PROPS: Record<string, BakedMesh> = {
  tree: {
    format: 7, stride: 28, vertexCount: 240, weightCount: 0, triCount: 62,
    aabb: { min: [-0.17732,-0.05,-0.20475], max: [0.17732,1.46944,0.20475] },
    vertices: dcU8('nature:tree.vertices'),  // <- pulled from .dcpak
    indices: dcU16('nature:tree.indices'),
  },
};
```

At runtime a game wraps a `BakedMesh` into an uploadable mesh with one call —
`meshFromBaked` reuses the decoded bytes (no copy) and hands `vertices.buffer`
straight to the host uploader:

```ts
import { meshFromBaked, NATURE_PROPS } from "@dreamcart/framework";
const tree = meshFromBaked(NATURE_PROPS.tree); // uploaded once; drawn each frame
```

**Skinning is partitioned at bake time.** The PSP GE has no bone-index palette: a
single skinned draw binds at most a handful of matrices, with weight slot *i*
paired to matrix slot *i*. So a rig with more joints than the bone limit (the Fox
has 24) is split **by triangle** into batches whose joint set fits the limit; the
baker remaps each batch's joint indices to local slots and reorders the weights to
match. The generated `assets-fox.ts` therefore lists several `batches`, each its
own `BakedMesh` plus a `jointTable`, alongside the shared bind pose, inverse-bind
matrices, and resampled clips:

```ts
export const FOX = {
  scale: 0.03, jointCount: 24, boneLimit: 4,
  jointParents: dcI8('fox:jointParents'),
  inverseBindMatrices: dcF32('fox:inverseBindMatrices'),
  bind: { t: dcF32('fox:bind.t'), r: dcF32('fox:bind.r'), s: dcF32('fox:bind.s') },
  batches: [ /* one BakedMesh + jointTable per bone batch */ ],
  clips: {
    Walk: { fps: 24, frameCount: 18,
      t: dcF32('fox:clip.1.t'), r: dcF32('fox:clip.1.r'), s: dcF32('fox:clip.1.s') },
    // Survey, Run …
  },
  texture: { width: 128, height: 128, psm: PSM_8888, pixels: dcU8('fox:texture.pixels') },
};
```

All the trig — quaternion slerp, the resample to a fixed `fps`, the inverse-bind
math — runs in the baker. The runtime animation sampler just lerps between two
baked frames (see [3D](3d) for the native skinning + sampler path).

Textures decode from PNG, box-downsample to a power-of-two ≤ 256², and pack to a
PSP pixel format (`PSM8888`). A `BakedTexture` carries `width`, `height`, `psm`,
and the raw `pixels` blob.

### Data-driven scenes

`bake-scene.ts` serializes a `SceneDescriptor` (prototypes + instance transforms
+ colliders) into three blobs per scene key, which the runtime reads back with
`loadScene(key)`:

```
"<key>:scene.meta"       DT_U8   UTF-8 JSON: camera/fog/prototypes + instances
"<key>:scene.xforms"     DT_F32  every transform triple, in add order
"<key>:scene.colliders"  DT_F32  min/max per collider (6 f32 each; may be empty)
```

This keeps a level's geometry references and layout out of the game's code path.
See the [3D](3d) and [Framework SDK](framework) docs for `loadScene` and the
scene description format.

## The .dcpak container

`.dcpak` (DreamCart PAcK) is a small, flat, **little-endian** binary container.
Every host (PSP, Web, 3DS, Android, the Bun test harness) reads the exact same
bytes — PSP, ARM/x86 build machines and browsers are all little-endian, so typed
arrays view the blobs directly with no byte swapping. The master store
`assets.dcstore` and every per-game `<game>.dcpak` use this one format.

### Layout

```
+-----------------------------------+  offset 0
| Header (32 bytes)                 |
+-----------------------------------+  dirOffset
| Directory: entryCount × 24 bytes  |
+-----------------------------------+  namesOffset
| Name table (ASCII keys)           |
+-----------------------------------+  blobsOffset (16-aligned)
| Blob region (each blob 16-aligned)|
+-----------------------------------+  fileSize
```

**Header (32 bytes):** `magic` `0x4B504344` (`'DCPK'`), `version` (`1`), `flags`,
`entryCount`, and the offsets `dirOffset` / `namesOffset` / `blobsOffset`, then
`fileSize`. **Directory entry (24 bytes):** an FNV-1a-32 `keyHash` (quick reject),
the blob's `blobOff` + `byteLen`, the key's `nameOff` + `nameLen`, and a `dtype`
code. Entries are sorted by key, so a reader may binary-search; the reference
reader builds a hash map.

The `dtype` byte is advisory — it records the element type so the consuming module
picks the right accessor:

| dtype | element | accessor | TypedArray |
|------:|---------|----------|------------|
| 0 | u8  | `dcU8`  | `Uint8Array` |
| 1 | i8  | `dcI8`  | `Int8Array` |
| 2 | u16 | `dcU16` | `Uint16Array` |
| 6 | f32 | `dcF32` | `Float32Array` |

(`i16`, `u32`, `i32`, `f64` codes also exist.) `byteLen` is always a whole
multiple of the element size.

### Keys & per-game subsetting

Keys are namespaced `"<module>:<path>"` ASCII strings, unique within a pack:

```
fox:inverseBindMatrices
fox:batch.0.vertices
fox:clip.1.t
nature:tree.indices
racing3d:scene.meta
```

The `<module>:` prefix is what makes the build ship only what a game uses. After
Bun bundles a game (non-minified), every key string a baked module references
appears **verbatim** in the bundle text. `framework/build.ts` builds each game in
isolation (so Bun tree-shakes it independently), then subsets the master store —
including a blob only when its key occurs as a quoted literal in that bundle:

```ts
const quoted = (bundle, lit) =>
  bundle.includes(`"${lit}"`) || bundle.includes(`'${lit}'`);
```

So a 2D game (snake, pong) or a procedural-mesh demo carries an **empty pack** (or
none), while a game that imports the Fox carries only the Fox blobs. Scene blobs
are matched by their `loadScene("<key>")` call instead of the raw key, since the
three scene keys are built by runtime string concatenation.

### Reading at runtime

The host loads the per-game pack and exposes its bytes as the global
`ArrayBuffer` `__dcpak` **before** the game bundle is evaluated. The reader
(`framework/src/dcpak.ts`) parses the directory lazily on first access and returns
each blob as a typed array over a **fresh copy** of the blob bytes — so
`arr.buffer` is exactly that blob, matching the old `unb64('…').buffer` semantics
that `meshFromBaked` relies on. The copy is one `memcpy` per blob, negligible next
to the base64 parse it replaces.

```ts
import { dcU8, dcF32 } from './dcpak';
const verts = dcU8('fox:batch.0.vertices'); // throws if the key is absent
```

### Delivery per host

The binary format is identical everywhere; only the transport differs:

- **PSP (Rust):** `runtime/build.rs` copies `<game>.dcpak` next to `game.js`;
  `main.rs` `include_bytes!`-embeds it and exposes it as `__dcpak` over the static
  `.rodata` slice (zero-copy, no file IO, never parsed by QuickJS).
- **3DS (C):** the build emits `game_dcpak.h` (`GAME_DCPAK[]` + len); `main.c`
  sets `__dcpak` before eval.
- **Web + Android:** `web/build-games.ts` embeds each game's pack (base64) in the
  generated manifest; `web/engine.js` decodes it to `__dcpak` before eval. Android
  runs the same WebView engine and inherits this path.
- **Test harness (Bun):** `framework/test/golden.ts` reads `<game>.dcpak` from
  disk and sets `globalThis.__dcpak` before evaluating the bundle.

A game with no baked assets runs with `__dcpak` unset; the reader only throws when
a missing key is actually requested.

### Versioning

`version` is bumped on any incompatible layout change, and readers must reject
unknown majors. The layout above is v1.
