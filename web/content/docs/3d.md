# 3D Engine

DreamCart's 3D layer is a continuation of its 2D model, not a new architecture.
The 2D contract is already "three independent native renderers behind a tiny data
contract" — `gfx.clear` / `gfx.fillRect` implemented per platform, with the shared
game `.js` holding all the logic. 3D keeps that exact shape: one shared scene graph
and all transform math live in JavaScript; each host owns only a thin native
renderer driven by a single batched command buffer per frame.

The whole native 3D surface is **one optional global, `g3d`**, sitting alongside
the 2D `gfx`. A host that supports 3D installs `g3d`; a 2D-only host leaves it
undefined and the framework silently skips the 3D pass. The same game bundle runs
on PSP (`sceGu`/`sceGum`), Web (WebGL2), and 3DS (`citro3d`) unchanged.

See also: the [runtime contract](../runtime-contract/) for the 2D `gfx`/`frame`
layer this builds on, [assets](../assets/) for how meshes and glTF characters bake
into the `.dcpak` pack, and [world import](../worlds/) for BSP map import.

## The g3d contract: upload once, batch one draw list per frame

Two ideas make 3D affordable on a 333 MHz PSP:

- **Retained meshes.** Geometry crosses the boundary exactly once. At init a game
  calls `g3d.uploadMesh(...)`; the host **copies** the bytes into its own storage
  and returns a small integer handle. A PSP cannot re-stream level geometry every
  frame, so static geometry is uploaded once and referenced by handle thereafter.
- **One `submit` per frame.** Each frame the shared JS assembles a single
  little-endian command/draw-list `ArrayBuffer` (a camera record plus one draw
  record per visible object) and hands it across in **one** `g3d.submit(...)`
  call. Per-frame FFI is therefore **O(1)** regardless of object count — a scene
  with 40 instanced cones is 40 draw records inside one buffer, not 40 calls.

The leaf native operation per draw record is exactly `loadMatrix(model)` +
`drawArray(handle)`, which maps 1:1 onto `sceGumLoadMatrix`+`sceGumDrawArray` on
PSP, `C3D_FVUnifMtx4x4`+`C3D_DrawArrays` on 3DS, and `uniformMatrix4fv`+
`drawElements` on Web — with zero reshaping. Critically, the bytes that cross the
boundary are *exactly* the bytes the golden test and the software reference
rasterizer consume, so determinism and testability fall out of the wire format
itself.

The 2D path is untouched: `gfx.clear`/`gfx.fillRect` become the HUD/overlay pass,
drawn **after** the 3D pass with depth disabled. A game that never touches `g3d`
renders byte-identically to today.

### The native surface

The full type lives in `framework/src/host3d.ts`. The three required methods:

```ts
interface RawG3d {
  // Upload a mesh ONCE; the host copies the bytes and returns a handle.
  // `vertices` is interleaved per `format`; `indices` is a Uint16Array buffer
  // or null for non-indexed. A host may draw indexed or expand to a flat buffer
  // (the PSP expands for VFPU 16-byte alignment) — the image must be identical.
  uploadMesh(vertices: ArrayBuffer, indices: ArrayBuffer | null,
             format: number, weightCount?: number): number;

  freeMesh(handle: number): void; // optional release; many games never call it

  // THE per-frame call: one batched command buffer, submitted once per frame
  // BEFORE any gfx.fillRect. The host clears depth, runs the 3D pass (depth ON),
  // then leaves depth OFF so the 2D HUD draws on top.
  submit(buffer: ArrayBuffer, byteLength: number): void;
}
```

Optional capabilities are probed individually (a host implements what its hardware
supports; the framework falls back otherwise):

- `uploadTexture(pixels, w, h, psm)` — retained textures (powers of two ≤ 512).
- `uploadSkin(buffer)` / `uploadClip(buffer)` — retain a skinned character +
  animation clip so sampling and bone math run **natively** (the PSP perf unlock
  for animated characters; see below).
- `sceneClear` / `sceneAdd` / `sceneSetEnv` / `sceneRender` — the **retained
  native scene**: upload an all-static scene once and let the host cull + draw it
  every frame, so JS only sends the camera. All four must be present together.

Two capability probes are exported for games and the framework:

```js
import { hasG3d, hasNativeScene } from '../src/index';
```

### The submit buffer (the cross-host wire format)

One little-endian `ArrayBuffer`, built by `framework/src/g3d.ts`'s
`CommandEncoder` into a pre-allocated buffer (default 256 KB, grown on demand):

```
Header (8 bytes):  u32 magic 'DC3D' (0x44433344) | u16 version | u16 recordCount
Record:            u16 opcode | u16 payloadWords (count of u32) | payload[...]
```

Every record is a whole number of u32 words, so the header and per-record headers
keep all f32/matrix payloads 4-byte aligned for typed-array views. The opcode set
is deliberately small (constants are the source of truth in `g3d.ts`):

| Opcode | Payload | Role |
|---|---|---|
| `OP_SET_CAMERA` | `viewProj` : 16 f32 (column-major, `proj·view`) | once per frame |
| `OP_DRAW` | u32 handle, u32 tintABGR, model : 16 f32 | per visible object |
| `OP_BIND_TEXTURE` | u32 texHandle (`0xffffffff` = unbind) | sticky texture state |
| `OP_SET_LIGHTS` | u32 count, u32 ambientABGR, count×{u32 colorABGR, 3 f32 dir} | ≤4 directional lights |
| `OP_SET_FOG` | u32 colorABGR, f32 near, f32 far | linear distance fog |
| `OP_DRAW_SKINNED` | `OP_DRAW` + u32 boneCount + boneCount×12 f32 | JS-skinned character |
| `OP_DRAW_SKIN_ANIM` | u32 skinHandle, u32 clipHandle, u32 tint, f32 phase, 16 f32 model | natively-skinned character |
| `OP_IMM_TRIS` | u32 vertexCount, u32 format, inline vertices | dynamic geometry (reserved) |

The magic + version header lets each native parser fail loudly on drift, and
`framework/test/contract.ts` asserts the opcode/format constants are byte-identical
across the JS, Rust (`runtime/src/gfx3d.rs`) and C (`runtime-3ds/source/main.c`)
copies.

### Cross-host conventions

These are pinned once in the `CROSS-HOST CONVENTIONS` block at the top of
`framework/src/g3d.ts` — the single source of truth — and enforced by the software
reference rasterizer (`framework/test/raster3d.ts`):

- **Matrices** are column-major (`m[col*4 + row]`), column vectors (`v' = M·v`),
  16 contiguous f32. They load verbatim into `sceGumLoadMatrix`,
  `C3D_FVUnifMtx4x4`, and `gl.uniformMatrix4fv(..., transpose=false)`.
- **Depth is reversed-Z.** The projection emits NDC z near→1, far→0; every host
  clears depth to the **far** value and keeps the **nearer** (GREATER) fragment.
  This is realized per host (one NDC contract, three native mappings): Web uses
  `EXT_clip_control ZERO_TO_ONE` + `depthFunc(GREATER)`; PSP uses
  `sceGuDepthRange(0, 65535)` + `GreaterOrEqual`; 3DS negates the mvp z-row into
  the PICA200's `[-w,0]` range + `C3D_DepthMap(true,-1,0)` + `GPU_GEQUAL`.
- **Y / winding.** NDC is Y-up; the flip to the Y-down framebuffer is each
  renderer's viewport job, **not** baked into the shared projection. Back-face
  culling is **disabled** on every host — occlusion is depth-only.
- **Color** is u32 ABGR with 0–255 channels; each host normalizes to [0,1] itself.

Because all rotation/projection math uses deterministic trig (`dsin`/`dcos`/`dsqrt`
in `math.ts`, never `Math.sin`/`Math.cos`, which differ in the last ULP across JS
engines), the emitted matrix bytes are **bit-identical on every host**, so the
draw-list golden compares byte-exact.

## Scene3D: the shared scene graph

Games rarely touch the encoder directly. `framework/src/scene3d.ts` provides a
`Scene3D` of `Node3D`s plus a `Camera`, mirroring the 2D `Scene`/`Node` tree.
Hand the scene to `engine.scene3d` and the engine walks it once per frame —
emitting one `OP_SET_CAMERA` and one `OP_DRAW` per visible node — before the 2D
HUD draw:

```js
// @ts-check
import { start, Scene, Scene3D, Mesh, Vec3, Quat, Colors, rgb, Btn } from '../src/index';
/** @import { UpdateContext, Graphics, Node3D } from '../src/index' */

class CubeScene extends Scene {
  /** @type {Scene3D} */ world = /** @type {any} */ (null);
  /** @type {Node3D} */ cube = /** @type {any} */ (null);
  rx = 0; ry = 0;

  /** @param {UpdateContext} ctx */
  onEnter(ctx) {
    this.world = new Scene3D();
    // 6 face colors: +X,-X,+Y,-Y,+Z,-Z. Uploaded ONCE on first draw.
    const mesh = Mesh.cube(1.4, [
      rgb(220, 70, 70), rgb(70, 180, 90), rgb(70, 110, 220),
      rgb(220, 200, 80), rgb(200, 90, 200), rgb(80, 200, 210),
    ]);
    this.cube = this.world.add({ mesh });
    this.world.camera.lookAt(new Vec3(0, 1.2, 3.6), new Vec3(0, 0, 0), new Vec3(0, 1, 0));
    // Hand the 3D scene to the engine — it auto-submits before the HUD.
    ctx.engine.scene3d = this.world;
  }

  /** @param {UpdateContext} ctx */
  update(ctx) {
    const d = ctx.input.dir();
    this.ry += (0.8 + d.x) * ctx.dt;
    this.rx += (0.5 - d.y * 0.9) * ctx.dt;
    this.cube.rotation = Quat.fromEuler(this.rx, this.ry, 0); // shared deterministic math
  }

  /** @param {Graphics} g */
  draw(g) {
    g.text('CUBE 3D', 8, 8, Colors.white, 2); // 2D HUD, drawn AFTER the 3D pass
  }
}

start(() => new CubeScene());
```

The game references only `Scene3D` / `Camera` / `Mesh` / `Quat` and the existing
`Graphics`. It never names a GPU, a matrix layout, or a platform — only flat
`Float32Array`s and a handle ever cross the boundary, so the **same** bundle runs
on PSP, Web, and 3DS. (This is `framework/games/cube3d.js`, available in the
[Playground](/play/).)

### Camera

`Camera` builds the column-major `viewProj = proj · view`:

```js
world.camera.setPerspective(60, 480 / 272, 0.1, 100); // fovDeg, aspect, near, far
world.camera.lookAt(eye, center, up);                  // Vec3s
```

`setPerspective` uses `Mat4.perspectiveReversedZ`. The `zeroToOne` flag (default
true) switches the projection for the WebGL fallback path where clip z is `[-1,1]`.
The eye position is kept for distance culling.

### Node3D

A node carries a transform plus an optional drawable:

```js
const node = world.add({
  mesh,                        // Mesh, or...
  material,                    // textured Material (Scene3D binds its texture)
  skinned,                     // SkinnedMesh (animated glTF character)
  position: new Vec3(0, 0, 0),
  rotation: Quat.identity(),
  scale: new Vec3(1, 1, 1),
  tint: 0xff8040,              // 0xRRGGBB, modulates the mesh color
  bounds: { min: [...], max: [...] }, // local AABB → frustum/distance culled
  isStatic: true,             // cache world matrix + bounds (see perf below)
});
node.add(child);              // children inherit the parent transform
```

`Scene3D` also tracks the currently-bound texture and emits `OP_BIND_TEXTURE` only
when it actually changes, so a scene that uses no texture emits zero bind records
(v1 goldens stay byte-identical).

## Mesh, material, light

### Mesh — procedural first

`framework/src/mesh.ts` generates geometry from code, so the cube/racing/FPS
examples need no asset files:

```js
Mesh.cube(size, faceColors);     // 6 face colors [+X,-X,+Y,-Y,+Z,-Z]
Mesh.box(w, h, d, faceColors);
Mesh.plane(w, d, color);         // horizontal plane on Y=0
Mesh.texturedCube(size, tint);   // adds FMT_UV + FMT_NORMAL (texture + lighting)
Mesh.solid(color);               // 6 identical face colors helper
```

For custom geometry, build vertices and triangles directly with `MeshBuilder`
(position + color) or `TexMeshBuilder` (adds UV + normal):

```js
const b = new MeshBuilder();
const a = b.vertex(-1, 0, 0, 0xff0000);
const c = b.vertex( 1, 0, 0, 0x00ff00);
const d = b.vertex( 0, 2, 0, 0x0000ff);
b.tri(a, c, d);          // or b.quad(i0, i1, i2, i3)
const mesh = b.build();
```

A `Mesh` holds interleaved vertex bytes and a `Uint16Array` index buffer. Bytes
are always packed in the PSP GE's mandated component order
`[weights][uv][color][normal][position]` (each 4-byte aligned), regardless of
which format bits are set — the bake step, the encoder, and every host agree on GE
order. The v1 layout is `[color u32 ABGR][pos 3 f32]`, stride 16. A mesh uploads
itself lazily on first `handle()` call and caches the result, returning -1 when
there is no 3D host.

Larger authored geometry is baked offline from glTF (`framework/bake/bake-gltf.ts`)
into a `BakedMesh`; `meshFromBaked(b)` wraps it into an uploadable `Mesh`. For
clumps of static scenery, `mergeMeshes(parts)` bakes many transformed meshes into
**one** mesh so they draw as a single GE call — the per-draw cost dominates large
scenes, and real PSP T&L eats the merged vertex count for free. See
[assets](../assets/) for the bake pipeline.

### Material + Texture

A `Texture` wraps pixel bytes in a `PSM_*` format (`PSM_5650`/`5551`/`4444`/`8888`
— the 16-bit formats halve VRAM, preferred on the tight PSP) and uploads lazily,
exactly like a mesh. A `Material` pairs a texture with a base color; a `Node3D`
references one so `Scene3D` binds the texture before that node's draw. UVs come
from `Mesh.texturedCube` or a `TexMeshBuilder({ uv: true })`.

### Lighting + fog

The PSP GE does T&L in hardware: up to **4 directional lights** plus a global
ambient, applied per-vertex using each mesh's `FMT_NORMAL`. JS only describes the
lights; `Scene3D` emits one `OP_SET_LIGHTS` per frame:

```js
import { Lighting, DirectionalLight, Vec3 } from '../src/index';
const lighting = new Lighting(0x202020);                       // ambient
lighting.add(new DirectionalLight(new Vec3(-1, -2, -1), 0xffffff));
world.lighting = lighting;
world.fog = { color: 0x88aacc, near: 20, far: 120 };           // linear distance fog
```

Fog fades geometry to its color between `near` and `far` (view-space distance) and
doubles as a draw-distance cap — set the fog color to match the background clear so
distant geometry fades into the sky. Lit meshes must carry normals
(`TexMeshBuilder({ normal: true })` or `Mesh.texturedCube`).

## glTF hardware skinning

Animated characters (e.g. the Khronos **Fox** — 576 tris, 24 joints, 3 clips) are
baked from glTF into a `BakedSkin` and wrapped in a `SkinnedMesh`:

```js
import { SkinnedMesh, Scene3D } from '../src/index';
import { FOX } from '../src/assets-fox'; // baked skin imported DIRECTLY (kept out of 2D packs)

const skin = SkinnedMesh.fromBaked(FOX);
skin.play(FOX.clips.Walk);              // start/switch a clip → returns the AnimationPlayer
world.add({ skinned: skin });

// each frame:
skin.player.advance(ctx.dt);            // sample the clip
```

The GE skins in hardware (`sceGuBoneMatrix` + `WEIGHTSn`). It has no bone-index
palette, so the mesh is partitioned at bake time into batches of ≤ `boneLimit`
joints; per frame `bone[slot] = jointWorld[jointTable[slot]] · inverseBind[...]`.
There are two paths, selected by host capability:

- **JS skinning + `OP_DRAW_SKINNED`** (fallback): JS samples the clip, walks the
  joint hierarchy, computes the ≤8 final 3×4 bone matrices per batch, and ships
  them over the wire. Works on every host with `g3d`.
- **Native skinning + `OP_DRAW_SKIN_ANIM`** (when the host has `uploadSkin` +
  `uploadClip`): the skeleton and clip are retained once; per frame JS ships only
  the clip **phase** ∈ [0,1) and the host samples, composes locals, walks the
  hierarchy, computes bones, and draws — all in native code.

The native path exists because per-joint sampling and per-vertex `Mat4·Vec3` on a
333 MHz interpreted core is the bottleneck, not the GE. Moving it to Rust took the
Fox from **6 → 30 FPS** (hardware skinning), and adding the native animation
sampler took it **30 → 60 FPS**. `SkinnedMesh.emit` falls back to the JS path
automatically when the native capabilities are absent.

## The retained native scene + the PSP perf story

The headline PSP performance unlock is the **retained native scene**. For an
all-static scene (terrain, scenery, a baked BSP map), even one
batched `submit` per frame is too slow — not because of the GE or the FFI, but
because *walking the JS scene graph* (one `Mat4.compose` + `Mat4.multiply` + an
8-corner AABB transform + allocations per node) costs roughly ~1 ms/node on the
interpreted QuickJS core, which dominates a large scene.

The fix moves the per-frame cull + draw into Rust. When every drawable node is
static and the host implements the optional scene API (`hasNativeScene()`),
`Scene3D.render` uploads the flattened scene **once** via `sceneClear` / `sceneAdd`
/ `sceneSetEnv`, then each frame calls `sceneRender(camera, dyn, dynCount, post)`
sending only the 20-float camera (viewProj + eye + cull-far). The host frustum-
culls and draws every instance natively; JS does almost nothing. Small dynamic
subtrees (a moving car + wheels, an animated character) are still walked in JS and
appended as a per-frame instance list and an optional `post` command buffer, so the
host still clears only once.

This is why `Scene3D` distinguishes `isStatic` nodes: it flattens them into typed
arrays (`sModel` / `sAabb` / `sHandle` / `sTint` / `sTex`) once, and either uploads
them to the native scene or, on a non-native host, draws them with `emitFlat` — a
tight loop with no per-node object access that emits the **same records in the same
order** as the object walk (so the `.dc3d` golden is byte-identical), just far
cheaper. Frustum culling uses the four side planes derived from `viewProj` plus an
explicit far-distance cutoff (robust and convention-free under reversed-Z); culled
counts are exposed via `scene3d.culledCount` for HUD/profiling.

Supporting facts:

- A **segregated O(1) arena allocator** on PSP fixed kernel-object exhaustion that
  large 3D scenes hit; together with native scene offload it is what makes the
  hardware max-out outdoor scene (Kenney nature props + a directional light + fog)
  hold its 30 FPS target.
- Static scenery should be **merged** (`mergeMeshes`) and animated by matrices
  only; keep dynamic geometry small. Triangle budgets are bounded by JS-side
  per-frame work + the single FFI crossing, not the GE's ~35 M-poly/s peak.

## Determinism & testing

Pixel-exact goldens across three real GPUs are impossible, so the authoritative
golden moves from the framebuffer to the **boundary payload**, which is
deterministic:

- **Draw-list golden** — a `g3d` mock records every `uploadMesh` and `submit`; the
  recorded stream is compared byte-exact (matrix floats are bit-identical thanks to
  the deterministic trig) against a committed `.dc3d` blob.
- **Software reference rasterizer** (`framework/test/raster3d.ts`) — a pure-JS
  triangle rasterizer consumes the *same* submit buffer and renders into the
  existing `W×H×4` RGBA buffer, then the normal PNG/`.rgbz` golden machinery runs.
  This is the human-viewable oracle that pins winding, reversed-Z, and matrix
  layout; each native host approximates it (threshold, not byte-exact).
- **Contract parity** (`framework/test/contract.ts`) — asserts the opcode, format,
  and depth constants are identical across the JS/Rust/C copies, plus a
  no-`Math.sin|cos|sqrt|tan` grep over `g3d.ts`/`math.ts`/`scene3d.ts` so the
  bytes stay deterministic.

The existing 2D goldens are untouched: 2D games never call `g3d`, and a 3D feature
is added only when a game needs it.
