# 为什么我的立方体会"内外翻转"？——一个关于深度缓冲的故事

> 我们做了一个能在 PSP、Web、3DS、安卓四种设备上跑同一份 JS 代码的 3D 游戏引擎。
> 一个再简单不过的"旋转立方体"，却在每个平台上都先翻了一次车：屏幕上不是一个
> 实心的方块，而是**像从内部看一个盒子**——能同时看到五个面，透视诡异得让人不安。
>
> 这篇文章用大白话讲清楚：这个 bug 到底是什么原理，为什么四个平台都中招，
> 以及它背后那套叫"深度缓冲"的、3D 图形学里最朴素也最容易出错的机制。
>
> 预备知识：你只要听说过"3D 模型是由三角形拼成的""屏幕是由像素组成的"就够了。

---

## 一、先看看"翻车现场"长什么样

正常情况下，你从外面看一个立方体，**最多只能看到 3 个面**（正面 + 上面 + 一个侧面）。
这是常识：一个不透明的盒子，背面永远被正面挡住。

但我们的 bug 画出来的东西是这样的：

- 正中间一个面（比如品红色）；
- 上下左右**四个面像画框一样围着它**，向四周张开。

加起来**五个面**。这在物理上是不可能的——除非你**站在盒子里面往外看**：背面是后墙，
四周是四面墙向你这边收拢。

所以这个画面本质上是：**该被挡住的"远处的面"显示了出来，该显示的"近处的面"反而没了。**
近和远，被调换了。

要理解为什么会这样，我们得先搞清楚：电脑到底是怎么决定"谁挡住谁"的。

---

## 二、电脑画 3D，第一步是"拍扁"

3D 世界是立体的，屏幕是平的。所以画 3D 的第一步，是把立体的点**投影**到平面上——
就像你拿手机拍照，三维的风景被"拍扁"成二维的照片。

这个"拍扁"由一个叫**投影矩阵**的东西完成。你不用懂矩阵，只要记住它干了两件事：

1. **算出每个点落在屏幕的哪个位置**（左右、上下）——这决定了形状；
2. **同时记下这个点离相机有多远**——这个"远近值"先记着，下一步要用。

第一件事如果出错，立方体会歪、会飞出屏幕。但我们的 bug 里，**位置是对的**
（立方体稳稳地在屏幕中央）。出问题的是第二件事——**远近**。

---

## 三、"谁挡住谁"靠的是一块记分牌：深度缓冲

把扁了之后，一个三角形会被拆成成千上万个**碎片**（fragment），差不多就是
"将要画到某个像素上的一小块颜色"。

问题来了：屏幕上同一个像素，可能有好几个碎片抢着要画。比如立方体正面的一个点，
和它正后方背面的一个点，拍扁之后**落在同一个像素上**。该画哪个？

当然是画**离相机近的那个**（近的挡住远的）。可电脑怎么知道谁近谁远？

答案是一块叫**深度缓冲**（depth buffer，又叫 Z-buffer）的东西。你可以把它想象成
**一块和屏幕一样大的记分牌**：屏幕有多少像素，记分牌就有多少格子，每个格子里写着
一个数——"目前这个像素上，画着的东西离相机有多远"。

每画一个碎片，GPU 都做一次**深度测试**：

> 拿这个碎片的"远近值"，去和记分牌上对应格子里的数比一比。
> 如果它**更近**，就赢了：把它的颜色画上去，并把记分牌上的数更新成它的远近值。
> 如果它**更远**，就输了：直接扔掉，当它不存在。

一帧开始时，记分牌先被**清空成"最远"**（相当于说"这里目前什么都没有，无穷远")，
这样第一个来的碎片必定能赢、画上去。之后谁更近谁就覆盖谁。

这套机制简单又暴力，是几乎所有实时 3D 的基石。**它的全部正确性，就压在一句话上：
"近的赢"。** 一旦"近的赢"变成"远的赢"，灾难就发生了——这正是我们的 bug。

---

## 四、关键的细节：远近值，到底用什么数表示？

这里有个魔鬼藏在细节里。"离相机多远"这个值，存进记分牌时，**到底是"越近数越大"
还是"越近数越小"？**

这听起来像废话，但它是整个 bug 的核心。因为：

- 投影矩阵会把远近值**算成一个具体的数**，遵循某种约定（比如"近 = 1，远 = 0"）；
- 而深度测试有个**方向**：它要么是"**数大的赢**"，要么是"**数小的赢**"。

**这两者必须配套。** 如果投影说"近的点 = 大数字"，深度测试就必须设成"大的赢"；
反过来配错，就会变成"远的赢"——于是远处的背面覆盖了近处的正面，你就看到了盒子的内壁。

**这就是"内外翻转"的全部秘密。** 不是相机进了盒子，是"谁赢"的规则被设反了，
导致每个像素上**留下来的都是最远的那个碎片**，于是你看到的是物体最里面、最远的那层。

那为什么这么容易配错？因为"近 = 大还是小"这件事，**每个图形系统的约定都不一样**。

---

## 五、为什么我们偏偏选了"反着来"：Reversed-Z

最自然的约定是"近 = 0，远 = 1"（近的小，远的大，"小的赢"）。但我们四个平台
统一用了一个**反过来**的约定：**"近 = 1，远 = 0"**，业内叫 **Reversed-Z（反向 Z）**。

为什么要自找麻烦反着来？因为一个很现实的精度问题。

深度值是用**浮点数**存的。浮点数有个特点：**它在 0 附近的精度极高，离 0 越远越粗糙**
（能表示的数越来越稀疏）。而投影的数学（透视除法）天生会把**远处的深度值挤在一起**——
本来远处的物体深度差别就小，再加上浮点数在那个区间又粗糙，两者叠加，就会出现
**Z-fighting（深度打架）**：远处两个挨着的面，GPU 分不清谁前谁后，画面上一闪一闪
地"撕裂"。

Reversed-Z 是个巧妙的对冲：它把**近处**映射到浮点数**精度高的 0 附近**，
让浮点数的"高精度区"正好对上投影"最需要精度"的地方，两个非线性互相抵消，
深度精度在整个范围内都变得均匀。代价就是：你必须记得**现在是"近 = 1，远 = 0"**，
深度测试要设成"**大的赢**"（GREATER）、记分牌要清空成 0（最远）。

> 一句话：Reversed-Z 是用"把远近调个头"换来的精度红利。红利很香，
> 但你从此必须在每一个平台上、每一处深度设置上，都记得自己是"反着来"的。
> 我们四次翻车，全是因为某个地方"忘了自己反着来"。

---

## 六、同一个意思，四种方言：跨平台的真正难点

最绕的地方在于：**"近 = 1，远 = 0"这个约定，四个平台用四种不同的"方言"来实现，
而且每种方言默认的"远近值范围"和"谁赢"的方向还不一样。**

我们的投影矩阵是**所有平台共用的同一份**（这是整个项目的灵魂：逻辑只写一份）。
它吐出来的永远是"近 = 1，远 = 0"。但每个平台的 GPU 收到这个值之后的处理不同：

- **PSP**（老掌机）：深度范围用 `0..65535` 表示。投影给的"近 = 1"要映射到
  `65535`（大），深度测试设"大的赢"——配套，正确。我们第一次翻车，就是把这个
  范围设反了（用了 `65535..0`），相当于把"近 = 1"映射成了"小数字"，于是"远的赢"。
- **3DS**：它的 GPU（PICA200）有个怪癖，合法的深度范围是 `[-w, 0]`（负数区间！）。
  我们的"近 = 1"是正数，**直接超出了它的合法范围被裁掉**——所以一开始**整个立方体
  都不见了**（不是翻转，是干脆没画）。修法是在 3DS 这边把深度值整体搬进它的负数区间。
- **Web / 安卓**：浏览器（WebGL）默认把深度范围当成"近 = 0，远 = 1"那一套老约定。
  想用真正的 Reversed-Z，需要一个叫 `EXT_clip_control` 的扩展。**桌面 Chrome 有这个
  扩展**，所以网页版一次成功；但**安卓的 WebView 没有这个扩展**，代码退回到了
  "老约定 + 小的赢"的兜底分支——而我们的投影明明是"反着来"的，于是又一次"远的赢"，
  又一次内外翻转。

看出规律了吗？**同一个根因（投影是 Reversed-Z，但某处的深度设置没配套）
换了三身衣服，在三个平台上各演了一遍。** 安卓这次之所以让人意外，是因为它复用
了网页版的代码，而网页版在桌面浏览器上是好的——只有换到"没有那个扩展"的 WebView
环境，那段写错的兜底分支才暴露出来。

## 七、所以那个"五个面"的画面，到底是怎么来的？

把前面串起来，慢镜头回放一遍翻转的瞬间：

1. 投影算出：立方体正面（近）深度 ≈ 1，背面（远）深度 ≈ 0。**位置算对了**，
   所以方块稳稳在屏幕中央。
2. 深度测试本该"大的赢"（近的赢）。但因为配置写反，实际变成了"**小的赢**"。
3. 于是在每个像素上，**深度值小的（最远的）那个碎片活了下来**，近的反而被扔掉。
4. 结果：你看到的全是立方体**最远那一层**的面——也就是从外面本该被挡住的背面、内壁。
   正面、近处的面，全被判输扔掉了。
5. 视觉效果就是：**仿佛你钻进了盒子，背面成了后墙，四壁向你围拢**——五个面，
   透视诡异。

它根本不是"透视算错了"，而是"**留下来的是错的那一层像素**"。形状的骨架是对的，
被"谁挡住谁"的规则给挑反了。

---

## 八、修复，其实就一句话

四个平台的修法各不相同（改深度范围、搬进负区间、去掉错误的兜底分支……），
但它们解决的是**同一件事**：

> **让投影定下的"远近约定"，和深度测试的"谁赢方向"，重新对上。
> 保证"近的赢"。**

具体到安卓这次：投影永远是"近 = 1，远 = 0"，那么**不管浏览器有没有那个扩展**，
"近"算出来的深度值**总是更大的那个**。所以正确的做法是——**无条件**地清空成 0（远）、
设成"大的赢"（GREATER）。之前那段"没扩展就改用小的赢"的兜底逻辑，是基于一个
**错误的假设**（以为没扩展时投影会变成老约定），其实投影从头到尾都没变。删掉它，
四个平台就都对上了。

---

## 九、给"听说过一些图形学概念"的你，几条带得走的心法

1. **深度缓冲 = 一块"谁离得近"的记分牌。** 实时 3D 不挡光、不算遮挡关系，
   它只是逐像素地比一个数、留下赢家。简单到近乎粗暴，但够快。
2. **"谁赢"是有方向的，而方向必须和投影的约定配套。** 90% 的"物体内外翻转 /
   该挡的没挡住"都是这两者没对上。看到这种现象，第一反应就去查
   **深度清除值 + 深度比较函数 + 投影的远近约定**这三件套。
3. **Reversed-Z 是精度的银弹，但它要求你全程记得"自己是反着来的"。**
   用了它，就要在每个平台、每处深度设置上贯彻到底，否则就会像我们一样翻四次车。
4. **"同一份逻辑，多个后端"最难的不是逻辑，是后端们对'同一个约定'的不同方言。**
   真正稳的做法，是把这些约定（远近方向、Y 轴朝向、颜色范围……）**白纸黑字写成一处
   不变量**，让每个后端各自去适配它——而不是指望它们"碰巧一致"。我们最后就是把这
   三条约定，连同每个平台的具体实现，钉成了代码里一段权威注释。

---

*这个 bug 之所以值得写一篇文章，是因为它几乎是 3D 图形学的一道"成人礼"：
你迟早会画出一个内外翻转的物体，然后被迫真正搞懂——屏幕上那层薄薄的像素，
是怎么从一堆抢着上位的碎片里，一个一个比出来的。*
